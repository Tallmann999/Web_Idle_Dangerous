# Правила реализации и оптимизации версии для Poki

Дата фиксации: 2026-09-02  
Статус: `active_platform_rules`  
Платформа: `Poki HTML5`

## 1. Назначение документа

Этот документ является постоянным техническим правилом для разработки Poki-версии **Clicker Weapon Adventure**. Он определяет:

- выбор технологии;
- адаптацию под компьютер, планшет и телефон;
- поддержку горизонтального и портретного режимов;
- подготовку и загрузку графики;
- интеграцию Poki SDK и рекламы;
- ограничения производительности;
- критерии готовности публикационного билда.

Если старые документы по itch.io или GamePush противоречат этому документу, для Poki-билда применяются правила, описанные здесь. Перед публикацией актуальные требования Poki необходимо повторно проверить по официальной документации.

## 2. Зафиксированное техническое решение

### 2.1. Основной стек

- Игра остаётся на текущем стеке `React + TypeScript + Vite`.
- Полный перенос в Unity не выполняется.
- Полный перенос в Phaser не выполняется.
- Для текущего статичного боя без анимаций врагов отдельный игровой движок не требуется.
- Простые пули, попадания, числа урона, монеты и декоративные эффекты реализуются CSS-анимациями либо отдельным лёгким Canvas-слоем.

### 2.2. Когда можно пересмотреть решение

Phaser или другой 2D-движок рассматривается только если одновременно появляются несколько требований:

- сотни активных частиц или объектов в кадре;
- сложные анимационные состояния врагов;
- физика, столкновения или перемещение множества объектов;
- камера, шейдеры либо сложные боевые сцены;
- текущий DOM/Canvas-слой перестаёт обеспечивать стабильную производительность на мобильных устройствах.

Даже в этом случае предпочтителен гибридный вариант: React отвечает за интерфейс, экономику, карту, магазин и сохранения, а движок используется только внутри боевой сцены.

## 3. Один универсальный билд

Для Poki собирается один адаптивный HTML5-билд, работающий:

- на компьютерах;
- на планшетах;
- на телефонах в landscape;
- на телефонах в portrait.

Отдельные архивы для горизонтального и портретного режимов не создаются. Интерфейс перестраивается по размеру и ориентации viewport без перезагрузки игры и без потери прогресса.

Poki рекомендует поддерживать portrait: это повышает доступность игры на мобильных устройствах и делает игру подходящей для дополнительного формата Gamebar Display. Поддержка portrait означает возможность участия, но не гарантирует показ рекламы.

## 4. Правила адаптивного интерфейса

### 4.1. Landscape

В горизонтальном режиме сохраняется основная текущая композиция:

- арсенал слева;
- поле боя справа;
- лента зон сверху;
- основные разделы снизу;
- ключевые показатели в верхней панели.

Интерфейс должен пропорционально масштабироваться и проходить проверки как минимум на контрольных размерах Poki `640×360`, `836×470` и `1031×580`.

### 4.2. Portrait

Горизонтальный интерфейс запрещено просто уменьшать целиком. В портретном режиме используется отдельная компоновка:

1. Компактная шапка с золотом, общим DPS и уроном за клик.
2. Горизонтально прокручиваемая лента зон.
3. Поле боя как главный и самый крупный блок экрана.
4. Имя врага, уровень, HP и награда располагаются рядом с нижней частью боевой сцены.
5. Арсенал открывается как нижняя выдвижная панель или отдельный экран.
6. Карта, магазин и настройки открываются модальными или полноэкранными панелями.
7. Основные кнопки должны быть удобны для нажатия пальцем и не перекрываться системными safe-area.

### 4.3. Общие правила

- Определять компоновку через CSS media queries и ориентацию viewport, а не только через user agent.
- При повороте устройства не перезапускать бой, таймеры или прогресс.
- Фоны выводить через `object-fit: cover`/эквивалент с контролируемой точкой кадрирования.
- Врага и важные UI-элементы держать внутри центральной безопасной области.
- Не допускать прокрутку страницы или родительского iframe во время игрового ввода.
- Планшеты должны получать сенсорную схему управления.
- Проверять интерфейс минимум на `360×640`, `390×844`, `412×915`, `768×1024` и контрольных landscape-размерах Poki.

## 5. Планируемый объём контента

Базовый объём:

| Категория | Количество |
|---|---:|
| Оружие | 30 |
| Обычные враги | 80 |
| Боссы | 20 |
| Данжевые боссы | 10 |
| Типы пуль | 30 |
| Мини-иконки оружия | 30 |
| Биомы | 8 |
| Резерв дополнительного контента | 10% |

Ориентировочно проект должен поддерживать около 220 графических файлов без необходимости менять архитектуру.

## 6. Бюджет размера

Это внутренние целевые значения, а не официальные лимиты Poki:

| Категория | Целевой диапазон |
|---|---:|
| Фоны восьми биомов, включая нужные portrait-варианты | 3–5 МБ |
| 80 обычных врагов | 3–6 МБ |
| 20 боссов и 10 данжевых боссов | 2–4 МБ |
| 30 изображений оружия | 1–2 МБ |
| Пули, мини-иконки и UI | 1–2 МБ |
| Код, локальный шрифт и аудио | 1–2 МБ |
| Ориентир полного набора | 11–20 МБ |

Полный размер архива не должен становиться размером первой загрузки. Цель начальной загрузки — около 3–4 МБ либо меньше, если это возможно без заметной потери качества.

## 7. Правила подготовки исходников

### 7.1. Персонажи, оружие и эффекты

- Мастер-исходники передаются в PNG с прозрачностью либо в исходном PSD.
- Персонажи на спрайт-листе должны иметь достаточные промежутки, чтобы соседние части не попадали в нарезку.
- В исходнике не должно быть водяных знаков, чужих логотипов или случайного текста.
- Не выполнять несколько последовательных сжатий с потерями.
- Финальная конвертация в WebP производится один раз после нарезки и удаления прозрачных полей.
- У всех врагов должна быть согласованная точка опоры по уровню ног.
- Каждый итоговый файл получает плотную обрезку без лишних прозрачных полей.

Рекомендуемые максимальные размеры:

| Тип | Размер |
|---|---:|
| Обычный враг | до `512×512` |
| Крупный босс | до `768×768` |
| Оружие | около `384×256` |
| Мини-иконка | `96–128 px` |
| Пуля/попадание | `128–192 px` |

### 7.2. Фоны

- Каждый биом получает собственный фон.
- Композиция должна сохранять свободную центральную область для врага и боевого UI.
- Если один фон плохо кадрируется в обеих ориентациях, создаются `landscape`- и `portrait`-варианты.
- Через `<picture>`, media query или программный выбор загружается только вариант текущей ориентации.
- Не загружать одновременно обе версии фона без необходимости.

### 7.3. Атласы

- Не объединять всех врагов и всё оружие в один огромный атлас.
- Допускаются небольшие атласы внутри одного биома или одной категории, если они действительно уменьшают запросы и не заставляют загружать неиспользуемый контент.
- Для текущей React-архитектуры по умолчанию использовать отдельные WebP-файлы и манифест ассетов.

## 8. Прогрессивная загрузка

### 8.1. Первая загрузка

До первого игрового действия загружаются только:

- HTML, CSS и основной JS;
- локальный шрифт;
- стартовый экран или минимальный загрузочный экран;
- интерфейс первого боя;
- фон первого биома;
- текущее оружие и необходимые мини-иконки;
- первый враг;
- критические звуки первого взаимодействия.

### 8.2. Фоновая загрузка

После первого действия игрока:

- предварительно загружается следующий враг;
- затем остаток текущего биома;
- следующий биом загружается при приближении к его открытию;
- магазин загружает полноразмерное изображение оружия только при необходимости;
- закрытые дальние биомы не должны попадать в начальную загрузку.

Обычный атрибут `loading="lazy"` не считается достаточной системой. Необходим управляемый asset manifest и явный prefetch ближайшего контента.

## 9. Ограничения производительности

- В DOM одновременно находится только текущий враг; следующий может быть предварительно загружен как изображение без отображения.
- Переиспользовать объекты пуль, монет, попаданий и текста урона либо строго ограничивать их количество.
- Не создавать бесконечные массивы визуальных эффектов.
- Для частых перемещений использовать `transform` и `opacity`.
- `will-change` применять только к действительно анимируемым объектам.
- Не хранить все изображения врагов в декодированном виде в памяти.
- Останавливать анимации и игровые циклы, когда вкладка скрыта, открыто меню, идёт реклама или вызван `gameplayStop`.
- Проверять стабильность не только FPS, но и память после продолжительной игры и нескольких смен биомов.

## 10. Poki SDK

Для Poki создаётся отдельный platform adapter. Игровая логика не должна обращаться к GamePush или Poki напрямую.

Обязательные события:

- `gameLoadingFinished()` — после завершения критической загрузки;
- `gameplayStart()` — на первом игровом вводе и при возвращении к активному бою;
- `gameplayStop()` — при паузе, открытии прерывающего меню, окончании уровня, выходе на карту и других остановках gameplay;
- `commercialBreak()` — только в естественной точке перед возвращением к игровому процессу;
- `rewardedBreak()` — только после явного выбора игрока посмотреть рекламу за награду.

Запрещено:

- отправлять два одинаковых lifecycle-события подряд;
- запускать Poki-события во время активной рекламы;
- выдавать награду, если `rewardedBreak()` не подтвердил успешный просмотр;
- продолжать звук, ввод, автоурон или таймер активного боя во время рекламы;
- включать GamePush SDK, стороннюю рекламу или внешние рекламные запросы в Poki-билд.

## 11. Рекламные правила

- Rewarded-реклама всегда запускается добровольной кнопкой с понятным описанием награды.
- До нажатия игрок должен понимать, что будет показана реклама.
- Во время рекламы бой, ввод и звук ставятся на паузу.
- После рекламы прежняя пользовательская громкость восстанавливается.
- Награда выдаётся только при успешном результате SDK.
- Игровой баланс остаётся проходимым без рекламы.
- Реклама ускоряет или облегчает игру, но не блокирует обязательный прогресс.
- Тестовые двухсекундные рекламные заглушки не входят в публикационный Poki-билд.

## 12. Изоляция платформ

Рекомендуемая структура:

```text
platform/
  types.ts
  local.ts
  gamepush.ts
  poki.ts
```

Vite выбирает адаптер через переменную сборки. Poki-билд не должен импортировать GamePush-код и его внешние URL. itch.io/локальный билд использует локальный адаптер, если платформенный SDK не нужен.

## 13. Сохранения и внешние ресурсы

- Все обращения к `localStorage` оборачиваются в `try/catch`.
- Игра остаётся работоспособной в incognito даже при недоступном сохранении.
- Шрифты, библиотеки и игровые ассеты находятся внутри билда.
- Google Fonts и другие внешние CDN в Poki-билде не используются.
- Перед публикацией удаляются debug-инструменты, тестовые данные, исходники и неиспользуемые изображения.

## 14. Проверка в Poki Inspector

Перед передачей билда на проверку обязательно проверить:

- загрузку `index.html` без ошибок;
- отсутствие запрещённых внешних запросов;
- event log Poki SDK;
- отсутствие повторных lifecycle-событий;
- работу рекламы и корректную выдачу награды;
- отключение ввода и звука во время рекламы;
- landscape и portrait на телефоне;
- планшетную компоновку;
- контрольные размеры 16:9;
- отсутствие прокрутки страницы;
- предупреждения об оптимизации изображений;
- работу без localStorage;
- сохранение состояния при смене ориентации;
- загрузку следующего врага без видимой паузы;
- отсутствие роста памяти после нескольких биомов.

## 15. Definition of Done для Poki-билда

Билд считается готовым, только если:

1. Один архив работает на desktop, tablet и mobile.
2. Поддерживаются landscape и portrait с отдельной компоновкой, а не механическим уменьшением.
3. Первая игровая сцена появляется без загрузки всего контента.
4. Ассеты оптимизированы и распределены по биомам.
5. В памяти не удерживается весь набор врагов и боссов.
6. Poki SDK работает через изолированный адаптер.
7. GamePush и сторонняя реклама отсутствуют в Poki-сборке.
8. Рекламные паузы останавливают звук, ввод и gameplay.
9. Игра работает в incognito и при заблокированной рекламе.
10. Poki Inspector не показывает критических предупреждений.
11. Сборка протестирована на реальном телефоне в обеих ориентациях.
12. Все 8 биомов и магазин могут добавляться без изменения основной архитектуры.

## 16. Порядок реализации

1. Разделить платформенную интеграцию на адаптеры Local/GamePush/Poki.
2. Поместить Roboto Condensed и остальные обязательные ресурсы внутрь проекта.
3. Перестроить интерфейс для portrait.
4. Добавить asset manifest и загрузку по биомам.
5. Ввести единый конвейер нарезки и WebP-конвертации.
6. Подключить lifecycle-события Poki.
7. Заменить рекламные заглушки настоящими Poki-вызовами.
8. Проверить память, загрузку и отзывчивость на слабом телефоне.
9. Пройти все проверки Poki Inspector.
10. Собрать чистый публикационный ZIP.
